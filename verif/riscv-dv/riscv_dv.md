# Functional verification of RV32RocketConfig with riscv-dv

A random instruction program generated by riscv-dv is run on both **Rocket RTL
(Verilator)** and **Spike (ISS)**, and the architectural state (GPR writes) of
the two execution traces is compared.
Any mismatch is a candidate RTL bug.

```
riscv-dv pyflow -> .S -> riscv64-unknown-elf-gcc -> .elf
                                                    |-> spike (--log-commits)      -> spike log  --+
                                                    `-> Verilator RTL (commit log) -> rocket log --+
                                                                                                   `-> trace CSV comparison
```

> WARNING - **safety rule**: never run any make/build in the pristine
> a pristine chipyard tree.
> Build and run only in `CY=<chipyard tree>` (a dedicated copy).
> `run_riscv_dv.sh` checks this path at startup and refuses otherwise.

This document is command-oriented and copy-pasteable. The background and
troubleshooting log is in [`flow_notes.md`](./flow_notes.md).

## 1. Installing riscv-dv (pyflow mode)

riscv-dv is originally UVM/SystemVerilog (VCS/Questa) based, but it has a
**pyflow** mode (pure Python + PyVSC) that can generate instructions without a
commercial simulator. The supported ISAs are RV32IMAFDC / RV64IMAFDC,
**M-mode only**, which fits our core (RV32IMAC/IMC, M-mode, no MMU) exactly.

```bash
# clone
git clone https://github.com/chipsalliance/riscv-dv.git ~/repo_riscv/riscv-dv
cd ~/repo_riscv/riscv-dv

# Use a dedicated venv to avoid polluting the conda environment (pyflow runtime deps only)
python3 -m venv ~/repo_riscv/riscv-dv-venv
source ~/repo_riscv/riscv-dv-venv/bin/activate
pip install --upgrade pip
pip install PyYAML bitstring pyvsc tabulate pandas

# sanity check
python3 run.py --help | head -5
```

pyflow is slow: generating one 10k-instruction program takes about 5 minutes (a
known limitation, stated in the riscv-dv documentation).

## 2. RV32IMC / RV32IMAC target settings

riscv-dv's default targets do not include `rv32imac` (only `rv32imc`), so it was
added. The following files are already present in this repository copy:

| Path | Contents |
|---|---|
| `pygen/pygen_src/target/rv32imac/riscv_core_setting.py` | pyflow core settings (adds `RV32A` to `supported_isa`) |
| `target/rv32imac/` | testlist + the `.sv` core settings |
| `run.py` | the `--target rv32imac` -> `isa=rv32imac_zicsr_zifencei`, `mabi=ilp32` branch |

The core characteristics already match, being based on `rv32imc`:
`SATP_MODE=BARE` (no MMU), `supported_privileged_mode=[MACHINE_MODE]` (no S/U),
`support_pmp=0`, `support_sfence=0` -> no paging or S-mode tests are generated.

The generated code has `misa = 0x40001105` (MXL=RV32, bit0=A, bit2=C, bit8=I,
bit12=M), confirming IMAC.

**The effective verified scope today is RV32IMC** (A is blocked by a generator
bug - see section 7).
So the flow below uses the `rv32imac` target, but the instructions that actually
come out are IMC.

## 4. The whole flow (manual, step by step)

Unrolled by hand, this is what `run_riscv_dv.sh` does internally.

### 4-1. Generate + gcc + spike (riscv-dv `run.py`)

```bash
source $VENV/bin/activate
export RISCV_GCC=$RISCV/bin/riscv64-unknown-elf-gcc
export RISCV_OBJCOPY=$RISCV/bin/riscv64-unknown-elf-objcopy
export SPIKE_PATH=$RISCV/bin

cd $DV
python3 run.py \
  --target rv32imac \
  --test riscv_arithmetic_basic_test \
  --simulator pyflow --iss spike \
  --steps gen,gcc_compile,iss_sim \
  -o $WORK/demo --iterations 1 --seed 1000 \
  --sim_opts="--stack_len=5000 --tvec_alignment=7"
```

Artifacts:
- `$WORK/demo/asm_test/riscv_arithmetic_basic_test_0.S`  (the generated assembly)
- `$WORK/demo/asm_test/riscv_arithmetic_basic_test_0.o`   (the ELF)
- `$WORK/demo/spike_sim/riscv_arithmetic_basic_test_0.log` (the spike commit log)

> `--sim_opts` must be attached with `=`. Its value starts with `--`, so passing
> it separated by a space would be parsed as another option.

### 4-2. Rocket RTL run (Verilator)

```bash
cd $CY/sims/verilator          # <- must be chipyard-riscv-dv
ELF=$WORK/demo/asm_test/riscv_arithmetic_basic_test_0.o

./simulator-chipyard.harness-RV32RocketConfig \
  +permissive +verbose "+loadmem=$ELF" +permissive-off "$ELF" \
  > $WORK/demo/rtl_sim/rocket.raw.log 2>&1
```

- `+permissive ... +permissive-off` : wraps the plusargs so HTIF does not mistake
  them for the binary
- `+verbose` : enables the commit trace printf (the commit log is gated by
  `printf_cond = verbose && !reset`)
- `+loadmem=<elf>` : **the key.** Loads the ELF straight into the backing memory
  through the DPI backdoor.
  Without it, fesvr spends millions of cycles pushing the image over serial TSI
  and it looks stuck (over 2 minutes for a 40KB image -> 8.3 s with `+loadmem`).

### 4-3. Trace CSV conversion + comparison

```bash
source $VENV/bin/activate

# The commit log has no disassembly, so append DASM(bits) and pipe through spike-dasm
sed -E 's/^([0-9] 0x[0-9a-f]+ \(0x([0-9a-f]+)\).*)$/\1 DASM(\2)/' \
    $WORK/demo/rtl_sim/rocket.raw.log \
  | $RISCV/bin/spike-dasm > $WORK/demo/rtl_sim/rocket.log

# The program ends with ecall and traps. The spike converter stops at ecall, so the
# RTL trace is also cut at the trap entry point (mtvec_handler); after that is the tohost handler.
END=$($RISCV/bin/riscv64-unknown-elf-nm $ELF | awk '$3=="mtvec_handler"{print "0x"$1}')

cd $DV
python3 scripts/spike_log_to_trace_csv.py \
  --log $WORK/demo/spike_sim/riscv_arithmetic_basic_test_0.log \
  --csv $WORK/demo/rtl_sim/spike.csv

python3 scripts/rocket_log_to_trace_csv.py \
  --log $WORK/demo/rtl_sim/rocket.log \
  --csv $WORK/demo/rtl_sim/rocket.csv --end_pc $END

python3 scripts/instr_trace_compare.py \
  --csv_file_1 $WORK/demo/rtl_sim/spike.csv  --csv_name_1 spike \
  --csv_file_2 $WORK/demo/rtl_sim/rocket.csv --csv_name_2 rocket_rtl
# -> [PASSED]: N matched   or   [FAILED]: ... mismatch
```

## 6. How the RTL trace was obtained

### Why the default `+verbose` did not work

Rocket's default `+verbose` trace prints writes as `W[r10=..][wen]` on one line,
but because of `coreMonitorBundle.wrenx = wb_wen && !wb_set_sboard` in
`RocketCore.scala`, **every long-latency writeback that goes through the
scoreboard (load, mul/div) comes out with `wen=0`.**
That is, the destination register is not visible in the trace at all.
Verification of RV32I**M**AC does not hold if loads and M are missing (on the 10k
test: `[FAILED] 73 matched, 2176 mismatch`).

### Solution: enable the rocket-chip commit log

`RocketCore.scala` has a separate spike-compatible commit log path with output
dedicated to long-latency writebacks (`x<rd> p<rd> 0x<data>`). It is enabled by
`enableCommitLog`.

```bash
# Already applied in this repo:
#   generators/rocket-chip/src/main/scala/tile/Core.scala  (val enableCommitLog)
#     val enableCommitLog = false   ->   true
```

`enableCommitLog` is a global `val` and cannot be split out into a chipyard config
fragment, so the source was edited directly and Verilator rebuilt. The existing
`+verbose` binary was backed up as
`simulator-chipyard.harness-RV32RocketConfig.verbose-backup`.

### How to rebuild (when needed)

```bash
cd $CY/sims/verilator           # <- must be chipyard-riscv-dv
pwd | grep -q '^<chipyard tree>/sims/verilator$' || { echo ABORT; exit 1; }
make CONFIG=RV32RocketConfig -j$(nproc)
```

WARNING: **`$CY/riscv-dv-flow/fix_gen_collateral.sh` must be run before the
rebuild.**
The 22 headers required by this copy's local `SimTSI.cc` modification in
testchipip are untracked and are not copied into `gen-collateral/`
automatically, so the C++ compile breaks. The script fills them in.
(See the "troubleshooting log" in `riscv-dv-flow/README.md` for details.)

### The commit log trace converter

riscv-dv only ships spike/ovpsim/sail/whisper/renode converters and **none for
Rocket, so one was written**: `$DV/scripts/rocket_log_to_trace_csv.py`. It
auto-detects both the commit log and `+verbose` formats.
The key point is pending-write handling: when `x<rd> p<rd> 0xXXXX` appears it is
queued, and the later `x<rd> p<rd> 0x<data>` retroactively fills in the original
instruction entry (execution is in-order single-issue, so a per-register FIFO
suffices).

## 7. Why the A extension is blocked

It is a **pyvsc version incompatibility**. It has nothing to do with the RTL or
with our settings.

The `rv32imac` target and core settings exist and `misa` reports IMAC
(`0x40001105`), but **AMO instructions are never actually generated.** Both paths
are blocked:

| Path | Failure point |
|---|---|
| mixing AMO into a random stream (`riscv_rand_instr_test`) | `riscv_instr_stream.randomize_gpr` -> vsc `SolveFailure`. The directed load/store stream reserves address registers, leaving a small `avail_regs` pool; adding AMO (which needs 3: rs1/rs2/rd) makes the constraints unsolvable |
| a dedicated AMO stream (`riscv_amo_test`) | `riscv_amo_instr_lib.py:41` `self.avail_regs = vsc.randsz_list_t(...)` -> **`AttributeError: 'NoneType' object has no attribute 'size'` on pyvsc 0.9.5** (it blows up during object construction) |

In short, pyflow's RV32A generation is broken with the combination riscv-dv
`b7a0b4b` + **pyvsc 0.9.5**.
(A `riscv_amo_test` entry was added to `target/rv32imac/testlist.yaml`, but
generation fails for the reason above.)

### What would be needed to do A later

> WARNING: **never touch the conda environment (`~/chipyard/.conda-env`).** Any
> pyvsc downgrade must happen strictly inside the dedicated riscv-dv venv
> (`$VENV`).

1. **Downgrade pyvsc (inside the dedicated venv only)**
   riscv-dv's pyflow AMO library assumes an older pyvsc API. `randsz_list_t`
   initialization is broken on 0.9.5, so it must be dropped back to the pyvsc of
   the era riscv-dv validated against.
   ```bash
   # Leave the existing venv alone and create an experimental one (unrelated to conda)
   python3 -m venv ~/repo_riscv/riscv-dv-venv-amo
   source ~/repo_riscv/riscv-dv-venv-amo/bin/activate
   pip install PyYAML bitstring tabulate pandas
   # Find and try the version riscv-dv pinned (example - the actually compatible version needs checking):
   #   pip install 'pyvsc==0.7.5'   and see whether add_mixed_instr / randsz_list_t get through
   python3 run.py --target rv32imac --test riscv_amo_test \
     --simulator pyflow --steps gen -o /tmp/amo_probe --iterations 1
   ```
   - A good starting point is checking which pyvsc version riscv-dv validated at
     the time, from its `.metrics.json` / CI (`.travis.yml`).
   - Once a compatible version is found, the `AttributeError` disappears, and the
     `SolveFailure` in `randomize_gpr` may also ease depending on the solver
     backend (boolector) version combination.

2. **Or write the AMO test by hand**
   Feed hand-written `.S` files (`lr.w`/`sc.w`/`amoadd.w` etc.) through the same
   `run_riscv_dv.sh` trace comparison pipeline, bypassing the riscv-dv generator.
   Hand-coded assembly can be supplied through the `--asm_test` path.

3. **Verification itself is already possible**
   Only A *generation* is blocked; the RTL/spike/trace-comparison pipeline runs
   fine on an ELF containing A instructions. So as soon as (2) produces an ELF, A
   verification follows immediately.

## 8. Limitations and next steps

### Current limitations

| Item | Status | Cause |
|---|---|---|
| RV32IMC random verification | works (2622 matched) | - |
| M-extension (mul/div) writeback | verified | the commit log |
| A-extension (AMO) | cannot be generated | pyvsc 0.9.5 incompatibility (section 7) |
| Load-heavy programs | cannot be generated | pyflow generates unencodable instructions such as `c.sw a3,-34(a5)` (negative/unaligned offset; the `add_mixed_instr` path bypasses the guard at `riscv_load_store_instr_lib.py:145`) |
| Generation speed | slow | ~5 min for 10k instructions, 20+ min with many sub-programs (a known pyflow limitation) |

> The load writeback **handling mechanism** itself was confirmed by (a) a
> synthetic log unit test (`lw t2:deadbeef`) and (b) all 574 mul/div
> instructions, which take the same `ll_wen` path as loads, matching.
> What is blocked is the generator side, "producing a load-heavy program".

### Next steps (in priority order)

1. **Run a multi-seed regression** - keep the pipeline as is and vary only the
   seed:
   ```bash
   for s in 1 2 3 4 5; do
     ./run_riscv_dv.sh -t riscv_arithmetic_basic_test -n 1 -s $s
   done
   ```
2. **Cover other tests** - `riscv_loop_test`, `riscv_jump_stress_test`,
   `riscv_no_fence_test`, `riscv_illegal_instr_test` etc. (base_testlist.yaml).
   Note that tests depending on load/store or AMO hit the limitations above.
3. **Cover load/store** - work around pyflow's `c.sw` bug (disable compressed
   with `+disable_compressed_instr=1`, or fix the guard), or feed hand-coded
   load/store assembly through `--asm_test`.
4. **A-extension** - the pyvsc downgrade in section 7 (dedicated venv) or
   hand-coded AMO.
5. **Automated regression + summary** - a wrapper that runs several tests/seeds
   and collects PASS/FAIL into a table.
