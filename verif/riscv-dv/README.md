# verif/riscv-dv - the riscv-dv random instruction verification flow (v304 integration)

Verifies RV32RocketConfig with **random instruction streams generated by riscv-dv**.

```
generate (pyflow) -> gcc -> spike (ISS) -> Rocket RTL (Verilator) -> trace comparison
```

If the two traces diverge, RTL and the ISA reference disagree about architectural
state = a **candidate RTL bug**.

**Recorded result: 10k random instructions, 2622 instructions matched
(`[PASSED]`)** - see `riscv_dv.md` section 5 for details.

---

| File | Contents |
|---|---|

| `riscv_dv.md` | the main document - background, results, limitations (the original of `$CY/docs/riscv_dv.md`) |
| `flow_notes.md` | the detailed troubleshooting log (the original of `$CY/riscv-dv-flow/README.md`) |

### What is **not** here - and why

This flow does not run from chip_platform alone. It requires **changes in two
other repositories**, and those files are not owned by chip_platform, so they are
**not copied here; only the application procedure is recorded.** Copying another
repository's files here would let them drift from the originals, leaving it
unclear which copy is authoritative.

1. **The chipyard copy** - `enableCommitLog` in
   `generators/rocket-chip/.../tile/Core.scala`
2. **The riscv-dv upstream clone** - new scripts / target settings +
   modifications to `run.py` and the config

Sections 2 and 3 below are those procedures.

## 2. The change to apply to the chipyard copy (1 file, 1 line)

Enable Rocket's **commit log**.

**File:** `$CY/generators/rocket-chip/src/main/scala/tile/Core.scala` (around line 147)

```scala
-  val enableCommitLog = false
+  val enableCommitLog = true
```

### Why it is needed

The default `+verbose` trace alone **does not constitute verification.**
`+verbose` reports `rf_wen` as 0 for long-latency writebacks (load, mul/div), so
**those destination registers never appear in the trace at all** - and a large
fraction of RV32IMAC instructions fall into that category. The commit log emits
a separate `x<rd> p<rd> 0x<data>` line when the write actually lands, so the
architectural state can be reconstructed completely.

### Rebuilding after the change

```sh
make -C $CY/sims/verilator CONFIG=RV32RocketConfig
$CP/verif/riscv-dv/fix_gen_collateral.sh RV32RocketConfig   # after every gen-collateral regeneration
```

`fix_gen_collateral.sh` works around the fact that this copy's
`testchipip/csrc/SimTSI.cc` is locally modified to support `+verif=` and pulls in
`verif_host.h` and friends, which are not registered as Chisel resources and are
therefore not copied into `gen-collateral/` (without it, the C++ compile dies
with `fatal error: verif_host.h: No such file or directory`). It is not specific
to riscv-dv but a **helper script that makes the tree compile**, and it must be
re-run every time a Verilator rebuild regenerates gen-collateral.

> WARNING: **Rebuild only in the dedicated copy.** Doing so in the pristine
> a pristine chipyard tree is forbidden.
>
> WARNING: **Two hardcoded paths** - these must be edited in another environment:
> - line 17 `CY=<chipyard tree>`
> - line 27 `STUB=<chipyard tree>/.../testchip_external_interrupts.h`
>   -> **It reads a header from the pristine tree.** It is read-only, so it does
>   not violate the safety rule ("never build in the pristine tree"), but be aware
>   that a **dependency on the pristine tree remains**. The reason for using this
>   stub is that the real header on the csrc side only declares the
>   `SimExtInterrupts` DPI functions while the implementation
>   (`SimExtInterrupts.cc`) is absent from the build file list, producing an
>   undefined reference. In the long run this stub should be brought into the
>   dedicated copy or into chip_platform (out of scope for v304).

### 3-3. `pygen/pygen_src/riscv_instr_gen_config.py` - 2 places

**(a) Add a `--stack_len` option.** The stack is emitted as explicit zeros and
inflates the image. On an RTL target loaded over serial HTIF, that translates
directly into simulation cycles.

```python
+        self.stack_len = self.argv.stack_len
```
```python
+        parse.add_argument('--stack_len', type=int, default=5000,
+                           help='Stack size in words. ...')
```

**(b) Fix the `tvec_ceil` alignment bug - this is an upstream bug.**

```python
-        self.tvec_ceil = math.ceil(math.log2((self.XLEN * 4) / 8))
+        self.tvec_ceil = math.ceil(math.log2(self.XLEN * 4))
```

A vectored mtvec must align BASE to `4*XLEN` **bytes** (a 4-byte entry per
interrupt cause, with XLEN causes). The original `/ 8` mistook `4*XLEN` for a
**bit count** and computed an alignment 8 times too small - **16 B at XLEN=32,
where Rocket actually requires 128 B**. Rocket enforces the real constraint
(`formTVec` in `CSR.scala` masks `mtvec[6:1]` at XLEN=32), so an under-aligned
handler **vectors into the middle of an instruction** while Spike traps to the
intended address -> the RTL falls into an infinite loop.

This bug is what made the initial runs look like "the RTL is stuck". Details in
`flow_notes.md`, "Troubleshooting log 3".

## 4. Running

```sh
./run_riscv_dv.sh                     # default: riscv_arithmetic_basic_test once
./run_riscv_dv.sh -t riscv_rand_instr_test -n 5 -s 12345
```

| Option | Meaning | Default |
|---|---|---|
| `-t <test>` | test name | `riscv_arithmetic_basic_test` |
| `-n <N>` | iteration count | 1 |
| `-s <seed>` | fixed seed (reproducibility) | random |
| `-k <words>` | stack size in words | 5000 |
| `-a <log2>` | trap-vector alignment (7 = 128 B, Rocket's requirement) | 7 |

Result: `[PASSED]: N matched` or `[FAILED]: ... mismatch`. Logs are in
`$WORK/<test>/rtl_sim/`.

### `+loadmem` is the key to the RTL run

Instead of pushing the ELF over the serial TSI link, it is loaded **directly into
the backing memory via DPI**. Without it, fesvr spends millions of simulation
cycles just transferring the image while the core sits in the boot ROM, and it
**looks stuck.**

## 5. Why this was not reproduced under v304

This stage **requires RTL traces, so a chipyard build (enabling the commit log
and rebuilding Verilator) must come first**. The v304 integration scope was
limited to **integrating the scripts and documents and writing down the
reproduction procedure**; it was not actually re-run.
The recorded result of 2622 matches remains in `riscv_dv.md` section 5.

To reproduce, set up the paths in section 0 and follow sections 2 -> 3 -> 4.

## 6. Known limitations (summary)

- **RV32A (AMO) generation is broken** - pyflow fails to generate AMO streams.
  `riscv_amo_test` cannot be run yet.
- **The load/store stream sometimes generates an unassemblable `c.sw`.**
- The program ends with `ecall` and traps, so the comparison **stops at the trap
  entry point (`mtvec_handler`)** - the trap handler and `tohost` write after
  that are not handled by the spike converter and would appear as false
  mismatches.

For the full list and the reasoning see `flow_notes.md` and `riscv_dv.md`
sections 7-8.
